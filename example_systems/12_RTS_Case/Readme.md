# Reliability Test System Overview

The reliability test system (RTS) provided herein is a 73-bus synthetic system with 120 lines (or tap transformers in PowerSystems.jl, which are treated as essentially identical to lines in our models) on 108 corridors with three zones. This system contained 5.42 GW of renewable resources, 9.45 GW of thermal resources, and had a peak load of 8.91 GW. For our testing, we multiplied the load by 2 to lead to more capacity expansion decisions. The RTS was provided by the Sienna team at the National Laboratory of the Rockies. The data is provided as a SQLite database that is parsed and loaded into PowerSystemsSinvestmentsPortfolios.jl (PSIP). The PSIP datastruct is then loaded into GenX. The version of GenX contained on this branch has been extended to load in systems from PSIP. 

In this work, we also include an "expanded RTS" that is twice the size as the original RTS. This system was formed by making a copy of the original RTS and arbitrarily placing five existing lines between this new copy and the original system. The load data and the availability of the variable renewable energy (VRE) resources were perturbed so that the system copy was not identical to the original, with the perturbed copy having slightly higher VRE available. 

The RTS did not initially contain candidate lines or candidate generators, so these had to be added synthetically. In the SQLite file, there are 120 candidate lines that were added and which are identical to the 120 existing lines. In this current implementation, we remove these and add the candidate lines manually. Candidate lines were added based on the existing line data. For each existing line, a corresponding parallel candidate line was added to each corridor. As our formulation supports line retirements, new lines, and reconductored lines, we include multiple types of lines in this case study. For existing lines with capacities at or below 200 MW, the new candidate line corresponding to that existing line would retire that existing line and had a capacity 2.5 times the original line. In addition, the reactance of that line was also divided by 2.5 (susceptance was multiplied by 2.5) so that its susceptance was scaled proportional to capacity. For existing lines with capacity greater than 200 MW, the corresponding candidate line was parallel to the existing candidate line and had a capacity 1.5 times the existing line with a reactance divied by 1.5. We also added 6 new lines on new corridors. Each zone had two new corridors (one candidate line per corridor) with the new corridors between the largest load in the zone and the largest combined existing generation resources that did not already have a corridor. Finally, all existing lines that did not support retirement also could be reconductored. Note that these changes are added directly to the system outside of the GenX source code. 

New generation resources were added to the original SQLite database and loaded via the GenX source code. Ten different technologies were added to each zone. These included one or more forms of solar and wind and different thermal plants (e.g., coal, nuclear, distillate oil, combustion turbines, and combined cycle plants). As these plants were added to zones, we had to determine locations of these plants at buses or nodes. To determine candidate nodes, we ran an LP relaxation of our system with the original load multiplied by 3 with no transmission expansion, with DCOPF constraints, and with each technology available on every node in every zone. Any nodes with new generation greater than 1 MW in the solution of the LP were treated as candidate nodes. This resulted in 22 total nodes (with 5, 8, and 9 locations across the different zones). For the case studies, we randomly select 3 nodes in each zone for each technology and treat these as the candidate locations for those technologies. For a few additional tests, we allowed only 1 technology location per zone and 5 technology locations per zone. 

To sipmlify the model, we also used a time domain reduction (TDR) strategy (see GenX.jl [documentation](https://genxproject.github.io/GenX.jl/stable/Tutorials/Tutorial_3_K-means_time_domain_reduction/#Time-Domain-Reduction)). Initially, when the PSIP data is loaded into the code, each technology is loaded into one location in its zone (e.g., if it can be built on three different nodes, it will be loaded onto the first option). Later, the technology is also expanded to the other allowed locations by calling `GenX.expand_new_cap_resources_to_nodal!`, where the other locations are also allowed (e.g., if there are three candidate nodes for the technology, calling this function will add the other two resources). In the cases where we considered 1 and 5 technology locations per technology per zone, and in the RTS case studies, TDR was called BEFORE the `GenX.expand_new_cap_resources_to_nodal!` function was called, but in the expanded RTS case, it was called after. This is important because TDR uses the technologies availability in creating clusters, and the clusters could change if there are more or less VRE technologies that GenX.jl sees. In other words, if there are 12 new variable renewable energy technologies (4 technologies in 3 zones in 1 location each), then TDR may create different clusters than if there are 36 new VRE technologies (4 technologies in 3 zones in 3 locations each). 


## How to run

Individual case studies can be run by the Julia scripts contained herein. Three main tests are included in this work for both the RTS and expanded RTS, contained in respective Julia scripts with the following endings, and called by the shell scripts in the directory `shell_scripts`. Several arguments are passed to these files from the shell scripts that indicate which speedup strategy to use, whether to use Benders Decomposition (BD) or generalized Benders Decomposition (GBD) and other test specific parameters: 
 * `_speedup_strategies.jl` - This file tests six different speedup strategies to improve the performance of BD or GBD tested on the system with all the candidate lines available and 3 technology locations per technology per zone for new generation. These speedup strategies are combinations of hot-starting with a transport model, solving an LP relaxation of the master problem, and using regularization/stabilization.
 * `_line_subsamplings.jl` - This file tests different random line samplings so that not every new line can be expanded. New generation requirements remained the same as in the `_speedup_strategies` file. Speedup strategies were likewise applied to this file.
 * `_change_generator_number.jl` - This file tests using either 1 or 5 locations per technology per zone to see what influence the number of locations has on performance. 

All tests were run with Julia v1.10.5 with the package versions contained in the Project.toml file in the `GenX.jl` directory. This GenX.jl directory can be activated as a Julia environment and instantiated to replicate these results. To activate the environment and instantiate the environment, the user can call: 

```julia
using Pkg
Pkg.activate("<insert_path_to_GenX.jl_directory_here>")
Pkg.instantiate()
```

### Note on Setup Parameters

While GenX is generally set up to use case runners (e.g., a user calls a function and interacts with the cod primarily through CSV and YAML files), this case study is designed to call GenX's internal functions and operate directly in the julia file, rather than through YAML settings files.

This also means that the settings dictionary that contains the settings files is modified directly in the `run_...` script. A brief explanation of these setup parameters may be helpful. These include: 
 * `DC_OPF` - whether to use DCOPF constraints
 * `bilinear` - whether to use the bilinear implementation rather than the big M implementation for the DCOPF constraints
 * `unfix_slacks` - used for running the transport model. The DCOPF model is "relaxed" into the transport model by setting this parameter to 1. This is the method used for hot-starting. Slacks are added to the flow constraints such that the flow is unconstrained by the voltage phase angles. To "turn off" the transport model without rebuilding the problem, these slacks are fixed to zero so that the DCOPF constraints are reapplied. This value is set to 1 when using the "warmstart" (hot-starting) setting so that the transport model is run first. 
 * `BD_warmstart_bigM` - whether to hot-start the linear DCOPF problem (the big M implementation). `unfix_slacks` should be set to 1 and `bilinear` should be set to 0. 
 * `BD_warmstart_bilinear` - whether to hot-start the bilinear DCOPF problem. `unfix_slacks` should be set to 1 and `bilinear` should be set to 0. Benders will run the hot-starting to optimality (which is an LP without bilinear constraints), and then the subproblems will be recreated with the bilinear formulation and without slacks. 
 * `BD_integer_routine` - whether to solve with an LP relaxation before running the integer problem. If `BD_warmstart_bigM` or `BD_warmstart_bilinear` are 0, then this will apply to the DCOPF problem. 
 * `BD_post_warmstart_integer_routine` - used if the user wants to do the LP relaxation on the DCOPF constrained problem AFTER doing the integer routine on the transport model as well. 
 * `BD_Stab_Method` - whether to use regularization (options are `"off"` or `"int_level_set"`). 
 * `BD_regularization_switch` - whether to turn regularization to `"off"` after the hot-starting and LP steps are finished. 
 * `BD_post_warmstart_ConvTol` - convergence tolerance for the final step after hot-starting and LP relaxation steps are finished.
